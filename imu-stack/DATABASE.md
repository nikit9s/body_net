# База данных IMU-stack

TimescaleDB (Postgres 16), подключение по умолчанию:
`postgresql://postgres:postgres@localhost:5433/imu`

Схема создаётся миграцией [migrations/imu_timescale_migrations.sql](migrations/imu_timescale_migrations.sql),
тип `dev_id` расширен до `BIGINT` миграцией [migrations/002_dev_id_bigint.sql](migrations/002_dev_id_bigint.sql)
(прошивка использует `uint32_t`, который не помещается в обычный Postgres `INT`).

Все значения ускорения — в **мили-g (mG)**, 1000 mG ≈ 1 g. Прошивка сама переводит
сырые LSB акселерометра BMA423 в mG перед отправкой (`firmware/twatch_imu_ble/twatch_imu_ble.ino`).

---

## 1. `imu_windows` — сырые окна отсчётов

Гипертаблица (партиционирование по `ts0`, чанк — 1 день). Хранит "сырые" окна акселерометра как есть, без агрегации.

| Поле    | Тип         | Значение |
|---------|-------------|----------|
| `dev_id`| BIGINT      | ID устройства (T-Watch), задаётся в прошивке константой `DEV_ID` |
| `seq`   | BIGINT      | Порядковый номер окна от конкретного устройства (счётчик `g_seq`, инкрементируется на каждое окно) |
| `ts0`   | TIMESTAMPTZ | Время начала окна (первого отсчёта в окне) |
| `fs_hz` | SMAL LINT    | Частота дискретизации акселерометра, Гц (по умолчанию 100) |
| `n`     | SMALLINT    | Число отсчётов в окне (128, `WIN_N` в прошивке) |
| `axes`  | SMALLINT    | Битовая маска присутствующих осей (сейчас всегда `0b111` = X, Y, Z) |
| `batt`  | SMALLINT    | Заряд батареи часов на момент отправки окна, % (0–100) |
| `ax`    | BYTEA       | Массив отсчётов оси X, `int16`, в mG (сырые байты, little-endian) |
| `ay`    | BYTEA       | Массив отсчётов оси Y, `int16`, в mG |
| `az`    | BYTEA       | Массив отсчётов оси Z, `int16`, в mG |
| `crc32` | INT         | Контрольная сумма кадра (в БД пишется как 0 — проверка CRC уже выполнена мостом `bridge`, в таблицу значение не прокидывается) |

Первичный ключ: `(dev_id, ts0, seq)`. Окна перекрываются на 50% (`OVERLAP_N = WIN_N/2`) —
это нужно учитывать при анализе временных рядов, т.к. соседние окна частично содержат одни и те же отсчёты.

- Сжатие (`timescaledb.compress`) через 3 часа, сегментация по `dev_id`, сортировка по `(ts0, seq)`.
- Retention: 30 дней.

## 2. `imu_features` — фичи, посчитанные по каждому окну

Гипертаблица (чанк — 7 дней). Считается воркером (`worker/imu_ingest_worker.py`) сразу после записи `imu_windows`.

| Поле         | Тип         | Значение |
|--------------|-------------|----------|
| `dev_id`     | BIGINT      | ID устройства |
| `seq`        | BIGINT      | Номер окна (см. выше) |
| `ts0`        | TIMESTAMPTZ | Время начала окна |
| `a_rms_mg`   | INT         | RMS (среднеквадратичное значение) магнитуды ускорения за окно, mG. Магнитуда = `sqrt(ax²+ay²+az²)` по каждому отсчёту |
| `a_peak_mg`  | INT         | Пиковое (максимальное) значение магнитуды ускорения в окне, mG |
| `tremor_hz`  | REAL        | Зарезервировано под частоту тремора (Гц). **Сейчас воркером не заполняется** (столбец всегда `NULL`) |
| `fall_flag`  | BOOLEAN     | Флаг возможного падения: `TRUE`, если `a_peak_mg > 3500` мG (константа `FALL_THRESHOLD_MG`) |
| `step_count` | INT         | Количество шагов, обнаруженных в окне (см. алгоритм ниже) |

Первичный ключ: `(dev_id, ts0, seq)`.

**Как считаются шаги:** магнитуда ускорения пропускается через однополюсный
IIR-фильтр верхних частот (`alpha=0.98`) и скользящее усреднение (окно 5 отсчётов),
затем ищутся локальные пики выше порога `200 mG` с "мёртвой зоной" не менее `0.25 с`
между соседними шагами (защита от двойного счёта одного шага).

- Сжатие через 6 часов, сегментация по `dev_id`.
- Retention: 180 дней.

## 3. `imu_agg_1s` — посекундные агрегаты

Гипертаблица (чанк — 7 дней). Одна строка на устройство на секунду; при поступлении нескольких окон,
попадающих в одну и ту же секунду, агрегаты объединяются (MAX по амплитудам, сумма по шагам).

| Поле        | Тип         | Значение |
|-------------|-------------|----------|
| `dev_id`    | BIGINT      | ID устройства |
| `ts`        | TIMESTAMPTZ | Секунда, к которой относится агрегат |
| `a_rms_mg`  | INT         | Максимум RMS-магнитуды среди окон, попавших в эту секунду, mG |
| `a_peak_mg` | INT         | Максимум пиковой магнитуды среди окон этой секунды, mG |
| `steps`     | INT         | Суммарное число шагов за секунду (накапливается по всем окнам) |

Первичный ключ: `(dev_id, ts)`.

- Сжатие через 6 часов, сегментация по `dev_id`.
- Retention: 180 дней.

## 4. `cagg_imu_agg_10s` / `cagg_imu_agg_1m` — непрерывные агрегаты (continuous aggregates)

Материализованные представления TimescaleDB поверх `imu_agg_1s`, обновляются по расписанию
(`add_continuous_aggregate_policy`) и используются API для быстрой отдачи графиков без
полного пересчёта по сырым данным.

| Поле            | Значение |
|-----------------|----------|
| `dev_id`        | ID устройства |
| `bucket`        | Начало временного интервала (10 секунд / 1 минута) |
| `a_rms_mg_max`  | Максимум `a_rms_mg` внутри бакета, mG |
| `a_peak_mg_max` | Максимум `a_peak_mg` внутри бакета, mG |
| `steps`         | Сумма шагов внутри бакета |

- `cagg_imu_agg_10s`: бакет 10 секунд, обновляется каждую минуту, окно рефреша — последний 1 день.
- `cagg_imu_agg_1m`: бакет 1 минута, обновляется каждые 5 минут, окно рефреша — последние 30 дней.

## Как данные попадают в БД

1. **Прошивка** (`firmware/`) — сэмплирует BMA423 на 100 Гц, переводит LSB → mG, собирает окна
   по 128 отсчётов (перекрытие 50%), упаковывает в бинарный кадр с CRC32 и шлёт по BLE.
2. **Bridge** (`bridge/bridge_ble_ws.py`) — принимает BLE-уведомления, собирает фрагментированные
   кадры, проверяет CRC, транслирует окно в JSON через WebSocket.
3. **Worker** (`worker/imu_ingest_worker.py`) — читает WebSocket, пишет сырое окно в `imu_windows`,
   считает фичи и пишет их в `imu_features`, обновляет посекундный агрегат в `imu_agg_1s`.
4. **API** (`api/main.py`) отдаёт `imu_agg_1s`/continuous aggregates и `imu_features` наружу для дашборда.
